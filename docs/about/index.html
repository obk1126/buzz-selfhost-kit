이 "작성 → 적대적 검증 → 수정" 루프가 크루의 기본 작업 단위입니다. 실전에서는 이 루프가 문서의 법적 리스크 표현을 배포 전에 잡아냈습니다.

1. 어떤 문제였나

혼자 여러 프로젝트를 병행하면 반복 업무가 쌓입니다. 기록을 지식베이스에 옮기는 일, 메신저 요청을 처리하고 정리하는 일, 매일 아침 상황 점검. 각각은 10~30분짜리지만 매일·매주 반복되고, 미루면 지식이 휘발됩니다.

핵심 판단은 "AI 도구를 더 쓰자"가 아니라 "업무를 분해해 위임 가능한 단위를 찾자"였습니다. 사람의 판단(무엇을 남길지)과 기계의 실행(수집·변환·게시·검증)을 분리하는 것부터 시작했습니다.

2. 무엇이 실제로 돌아가고 있나

에이전트 5기가 역할을 나눠 맡고, 아래 업무가 사람 개입 없이 정기 실행됩니다.

업무주기사람이 하던 것 → 지금
지식 자산 역수입매주 에이전트들이 실전에서 기록한 운영 문서를 개인 지식베이스로 자동 인제스트 → 깃 커밋·푸시. 방법론 노트 17종 자산화
메신저 상주 응대상시 슬랙·텔레그램 멘션으로 문서 작성·데이터 추출·파일 처리, 스레드 단위 맥락 유지
산출물 교차 검증작업마다 한 에이전트의 산출물을 다른 에이전트가 적대적으로 검증 — 법적 리스크 표현 사전 적발 이력
야간 자가 점검매일 진행 중 작업을 기다렸다가 클린 재기동, 완료 후 상태 보고 (워치독·자가치유)

구체 수치·내부 기록은 공개 범위에서 제외했습니다. 대신 체계 전체를 재현할 수 있는 킷을 공개합니다.

3. 구조 — 사람 1 × 에이전트 5

사람 (슬랙·텔레그램 멘션 / 워크스페이스 앱 · 모바일 QR 페어링) │ 채널에서 멘션 / 정기 워크플로우(cron) ▼ 자체 VPS ─ 메신저 브리지 + 셀프호스팅 워크스페이스 (Block Buzz 릴레이) │ 공유 컨텍스트 · 공동 원장 · 서명 감사추적 ├─ A 총괄·검증 ├─ B 문서화·지식 ├─ C 데이터·자동화 ├─ D 개발·스크립트 └─ E 브리핑·모니터링 (전원 systemd 상주) ↳ 기반: Claude Code / Codex — 기존 구독 로그인, API 키 불필요
  • 외부 SaaS 종속 없음 — 오픈소스 릴레이 직접 호스팅. 데이터·감사추적이 내 서버에 남습니다.
  • 비용 설계 — API 과금이 아니라 기존 구독 인증으로 동작하는 하네스.
  • 기억 격벽 — 에이전트별 기억 분리, 작업 사실은 공동 원장에만 기록.

4. 운영하며 수업료 낸 것들

구축은 하루, 정착은 두 달. 실제로 겪은 운영 함정 9가지를 전부 문서화해 킷에 포함했습니다.

테넌트 라우팅 — localhost 직결이 404가 나는 이유

릴레이는 Host 헤더로 커뮤니티를 찾는다. 서버 내부에서도 반드시 도메인(wss)으로 접속해야 한다.

CORS와 데스크톱 앱 — 서버 로그에도 안 남는 실패

앱 대부분은 네이티브 통신이지만 초대 발급 등 일부만 웹뷰 fetch라 CORS를 탄다. 프리플라이트 차단은 서버에 도달조차 않아 로그로 원인을 못 찾는다.

모바일 QR 페어링 404

페어링은 전용 사이드카가 받는다. 릴레이 이미지에 바이너리는 있지만 기본 compose에는 없어 별도 기동이 필요하다.

이미지 메타데이터 전면 거부

릴레이는 JPEG의 EXIF·ICC까지 전부 거부(422)한다. 생성 이미지·촬영본은 메타데이터를 벗겨서 올려야 한다.

CLI 첨부 화이트리스트

CLI가 클라이언트 단에서 이미지 4종+mp4만 허용한다. 문서 첨부는 릴레이가 아니라 CLI 쪽 패치가 필요하다.

응답 게이트 이중 잠금 — 소리 없이 버려지는 멘션

멤버 전용 릴레이에서 허용목록 설정은 이중 잠금이 된다. 신규 멤버의 멘션이 에러 없이 사라진다. 폐쇄 릴레이라면 게이트를 여는 쪽이 맞다.

root 실행과 샌드박스 플래그

root에서 에이전트 하네스는 샌드박스 플래그 없이는 권한 모드를 거부한다.

작업 디렉토리 오염 — 세션이 멈추는 조건

세션 아카이브가 쌓인 작업공간을 그대로 주면 SDK 세션이 멈춘다. 에이전트별 클린 작업공간 + 필요한 기억만 심볼릭 링크.

워크플로우 cron은 UTC — 요일까지 환산

평일 08:30 KST는 30 23 * * SUN-THU다. 요일 숫자 0은 거부되므로 이름 표기가 안전하다.

5. 왜 공개했나 — 확산이 목적

이 체계의 가치는 "내 서버에서 돌아간다"가 아니라 "남도 반나절이면 같은 체계를 세울 수 있다"에 있습니다. 설치 스크립트, systemd 템플릿, 정기 업무 예시, 운영 함정 대장, 이관 3층 체크리스트(인격·기억·정기 업무)까지 재현에 필요한 전부를 공개했습니다.

6. 이 사례가 말하는 것

  • 업무를 task로 분해하는 눈 — 판단과 실행을 분리하고, 실행을 역할 단위로 위임하는 설계.
  • 도입이 아니라 정착 — 두 달의 운영: 자가치유, 교차 검증, 기억 격벽, 함정 문서화.
  • 확산 가능한 형태로 남기기 — 한 사람의 노하우를 다음 사람의 반나절로 바꾸는 것.
